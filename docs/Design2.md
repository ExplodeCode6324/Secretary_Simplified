# Secretary_Simple 架构设计

版本：0.1  
更新日期：2026-09-13

本文件定义业务需求、整体架构。

## 1. 设计目标

### 1.1 需求
Secretary的设想是通过一个整体的认知模型，来实现普通agent无法实现的持续记忆和认知能力。持续存在且能自动整理关键事项、提醒和承诺，能在日常生活中提供可靠的唤醒、晨报和连续语音交互，并有稳定的执行器
来完成Master布置的实时或定时任务。


### 1.1 逻辑架构
用户交互层：负责与Master的交互，收集输入、展示输出、提供反馈。
-初版默认cli交互，设想版本为持续前台在线的移动设备app，通过语音/文字完成输入和输出。

核心层（Secretary_Core）：负责处理核心业务逻辑，理解需求、维护数据、世界建模、状态跟踪、生成任务井协调执行。
-通过四层记忆结构来维护Secretary记忆 ，包括World Model、Live World State、Consciousness State和Conversation State(context)。

数据层：持久化Secretary的记忆和运行状态，是Secretary Core的运行基础。
-存放事项、来源记录、世界状态、任务计划、执行记录、会话与上下文

执行层（Execution Runtime）：按计划或即时触发，调用合适的执行器完成任务
-包含任务调度器Scheduler，用于按计划（时间触发、事件触发、手动触发）分类并触发任务，包含任务派发、重试、超时处理
-包含实际的执行器Executor，按任务类型调用合适的执行器完成任务，包含执行结果回执、状态更新、异常处理。可以是具体程序，也可以是agent

外部资源层：提供外部数据和服务的接入
-当前包括github仓库、学校Canvas、特定文件仓库

 ### 1.5 存储按职责分组，首版不按模块分库
 物理上先使用同一个本机 SQLite 数据库，加一个受控文件目录。数据库访问仅开放给 P1、P2 的受控模块，App、CLI 和外部 Agent 不直连数据库。
数据分组	沿用的主要对象	写入归属
业务与长期认知	Item（事项）、ProfileFact（偏好与事实）	P1 业务与世界建模模块
来源及新鲜度	SourceRecord（来源记录）、SourceState（同步状态）	P1 数据接入模块
会话与认知连续性	ConversationEvent（会话事件）、ConversationState（会话状态）	P1 会话及整理模块
计划与执行	ScheduledJob（定时计划）、JobRun（执行记录）、AlarmSession（响铃会话）	计划由共享受控模块修改；执行和响铃状态由 P2 修改
产物与配置	Briefing（晨报）、VoiceProfile（音色配置）	P1 相应业务模块；音频进程提供处理结果
证据与变更	ChangeEvent（变更事件）、原文引用、执行证据、诊断文件	各权威模块保存自己的变更与依据

World Model 先是对现有业务数据与长期事实的组织；Consciousness State 先是一个有界派生视图。两者都不需要单独部署数据库或后台进程。
