## 2. 本轮发现并修正的具体问题

- 主分支源码和同号 npm 版本存在 Context 协议差异，已以 npm gitHead/tag 对齐完整源码，初始失败保留。
- 严格 TypeScript 编译发现第三方 optional peer 缺失，已显式锁定而非关闭类型检查。
- 最小沙箱首次因缺启动权限失败，已补精确启动规则，并同时断言正常执行与 EPERM 拒绝；不把启动崩溃当作隔离通过。
- 根预算分清用户请求与维护任务，防辅助整理成为无限免费旁路。
- 任务当前版本与不可变定义采用 deferred 外键，首建/修改同事务；终态任务不直接复活。
- 取消与许可消费以提交次序定义边界；已经消费的在途动作仍可能产生副作用，必须核查。
- 正式回复与流式草稿、已发送与已确认接收分别定义，避免恢复时重跑已完成任务。
- 数据删除允许正文 tombstone，审计只保留必要非敏感元数据；旧备份恢复须应用更新的删除记录。
- 补齐无任务聊天、旧任务晚通知和内部工具去重；实体创建、义务解决、文本对象生成有明确入口。
- 防止记忆维护事件自触发循环；补齐金额预留、原生 FD 文件访问、孤儿进程监督和删除台账顺序。

## 4. Master 优先复核

1. 持续增量 Consciousness 与独立任务/要求/承诺是否符合期望。
2. 主会话协调、子会话操作，以及原型单子任务的范围是否合适。
3. 普通事实/偏好自动接纳、外部来源待决的默认政策是否合适。
4. 真实资料、模型出口、保留/删除及费用政策是否需要调整。
5. P0—P6 文本核心、P7 唤醒/多任务/移动端的顺序是否合适。

这五项是对已给出完整默认方案的复核，不是把缺失技术设计交给 Master 决定。后续可直接按交接表构建；真实凭据和新增资源授权在实际接入时按范围补齐。
