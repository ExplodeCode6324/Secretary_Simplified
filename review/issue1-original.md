## AUD-01 / P1：对象半写入残留导致同内容持续失败

**代码位置：** [`src/store/objects.go`](https://github.com/ExplodeCode6324/Secretary_Simplified/blob/ac281ac2e3504ef215f9b69ee1b314e2db16adea/src/store/objects.go)，`PutObject()`。

### 问题描述与触发条件

当前按数据分类、媒体类型和内容计算稳定对象 ID，然后直接以 `O_CREATE | O_EXCL` 创建最终 `<id>.blob`，写入、同步文件和目录，最后插入 `object_ref`。

在创建最终文件后、完整写入前退出，或发生写入失败/磁盘满，会留下没有数据库引用的半文件。同内容重试命中相同路径；已有文件内容哈希不匹配时返回 `STORAGE_CORRUPTION: orphan object hash`，没有恢复这类未提交残留的路径。

`objectMu` 仅为进程内互斥；Core 与 Runner 均有调用对象存储的路径，不能用这个锁证明跨进程发布安全。另一个进程可能观察到未完成的最终文件。影响包括输入原文归档、执行产物及合成诊断对象，不意味着整个数据库损坏。

### 修改建议

- 完整写入同目录临时文件，检查写入结果并同步，再以明确的原子发布协议暴露最终文件；发布时处理同 ID 的跨进程竞争，不能覆盖已提交对象。
- 对相同内容的元数据插入做幂等处理；最终目录项的持久化、对象引用和发布顺序应一致。
- 区分 **未提交孤儿文件** 与 **已提交对象损坏**。前者可在锁/原子协议保护下隔离并重建；后者必须继续拒绝并报警。不得通过“哈希不一致就删除/覆盖最终文件”掩盖损坏。

### 验收标准

- [ ] 在临时文件半写入、发布前、发布后但元数据提交前分别注入退出/失败；重启后，同内容重试能成功，最终只有一个有效对象引用，字节和哈希正确。
- [ ] 预置无 `object_ref` 的损坏半文件，再执行同内容提交，可通过明确恢复机制完成；不得永久卡在同一孤儿哈希错误。
- [ ] 使用两个独立进程/Store 并发提交相同内容，不观察到半文件，不向调用者暴露未处理的唯一键冲突，最后得到同一完整对象。
- [ ] 篡改已有 `object_ref` 对应文件，读写路径仍拒绝，不静默重建、不覆盖、不删除原损坏证据。
- [ ] 定向测试及受影响模块竞态测试通过，记录提交和测试命令。

## AUD-02 / P1：后台超时/取消后 CoreWork 回执无法可靠收口

**代码位置：** [`executor/executor.go`](https://github.com/ExplodeCode6324/Secretary_Simplified/blob/ac281ac2e3504ef215f9b69ee1b314e2db16adea/src/executor/executor.go)、[`core/work.go`](https://github.com/ExplodeCode6324/Secretary_Simplified/blob/ac281ac2e3504ef215f9b69ee1b314e2db16adea/src/core/work.go)、[`store/work_repo.go`](https://github.com/ExplodeCode6324/Secretary_Simplified/blob/ac281ac2e3504ef215f9b69ee1b314e2db16adea/src/store/work_repo.go)、[`executor/remote_query.go`](https://github.com/ExplodeCode6324/Secretary_Simplified/blob/ac281ac2e3504ef215f9b69ee1b314e2db16adea/src/executor/remote_query.go)、[`store/runtime_memory.go`](https://github.com/ExplodeCode6324/Secretary_Simplified/blob/ac281ac2e3504ef215f9b69ee1b314e2db16adea/src/store/runtime_memory.go)。

### 问题描述与触发条件

Runner 单次执行使用 30 秒子上下文；模型调用另有 60 秒上限，后台请求还可能等待前台调用。Core `BeginWork()` 已持久化 `RUNNING` 后，若 Runner 超时取消 HTTP 请求，Core 仍用 `r.Context()` 执行 `FinishWork()`，收尾事务可能因上下文已取消而无法提交。

与此同时 Runner 可用父上下文记录 `RESULT_UNKNOWN`（结果未知）并把任务置为 `NEEDS_ATTENTION`（需处理）。随后 `RemoteCore.Query()` 对没有回执的 CoreWork 只返回未知，无法自动收口。`ScheduleMemorySlot()` 命中已有当前槽账本后返回旧 run，也不会创建替代任务。

**不能只把收尾改为不受取消影响的上下文：** `FinishWorkTx()` 还要求对应 `job_run` 为 `RUNNING`；若 Runner 先落成结果未知，迟到收尾仍可能失败。30 秒预算本身不是缺陷，缺陷在取消后的结算协议。

### 修改建议

- 业务执行上下文与收尾持久化上下文分离；收尾应有独立但有限时长的机会，不能无限后台执行。
- 定义同一 run/attempt/fence 的未知状态结算规则，支持 Runner 已先落未知时的受控对账。继续校验 `attempt_no`（执行次数）、`fencing_token`（执行代次隔离令牌）、命令身份及取消代次；旧执行不得覆盖新执行。
- 按能力区分“确定未发生业务副作用”“已有可验证结果”“仍无法确认”。只有有证据的无副作用失败才可按既有预算重试；已有结果应结算，不应重复执行；确实未知的保留未知并可诊断。
- 意识槽等程序任务应能通过持久回执/目标产物对账恢复，不能因为无效的 RUNNING 残留永久占住当前槽。
- 不通过单纯延长超时、无限重试或强制改成成功来掩盖问题。

### 验收标准

使用假模型和可注入超时，走实际 Core↔Runner HTTP/socket 通信路径，无需真实外部模型、无需长时测试：

- [ ] 后台请求尚在排队、未调用模型即被取消：有明确且持久的无业务副作用结果，不永久停在无回执 RUNNING；允许重试时遵守已有次数/预算。
- [ ] 模型调用中取消：回执或可诊断未知状态持久化；已确定无业务副作用的情况可按策略恢复。
- [ ] 结果产物已持久化、HTTP 回执丢失/保存中断：重启或对账能识别既有结果，不重复业务副作用。
- [ ] 强制 Runner 先写 `RESULT_UNKNOWN`，再让同代 Core 收尾：合法结果能受控结算，不因只接受 RUNNING 而永久悬挂。
- [ ] 旧 attempt/fence 回执及取消后的迟到结果不能重新执行任务、覆盖新状态或把取消任务误标成功；必要审计证据保留。
- [ ] 当前意识槽可结算为已完成、可重试失败或有明确原因的未知/终态，不因空回执残留永久占位。

## AUD-03 / P2：准入拒绝仍产生持久归档对象

**代码位置：** [`src/store/core_repo.go`](https://github.com/ExplodeCode6324/Secretary_Simplified/blob/ac281ac2e3504ef215f9b69ee1b314e2db16adea/src/store/core_repo.go)，`AcceptInput()`、`AcceptTyped()`、`archiveInput()`、`acceptInputTx()`。

### 问题描述与触发条件

请求经初步幂等检查后，先 `archiveInput()` / `PutObject()`，再进入包含队列容量和业务准入检查的事务。因此队列返回 `BACKPRESSURE`（队列满拒绝），或 Typed（结构化直达）业务回调失败回滚时，原文文件及 `object_ref` 可能已提交。

不同内容的持续拒绝负载仍可增长对象存储和备份。相同内容会去重；这是已认证本机入口下的资源治理问题，不描述为公网匿名攻击。现有“幂等键冲突不新增对象”测试覆盖的是提前拒绝分支，不能替代上述场景。

### 修改建议

协调正式对象引用、输入受理和业务事务；或引入明确的有配额、可追踪、可回收暂存状态。并发最终准入必须仍在事务内检查，不能只在归档前查询一次队列长度。

对被拒绝请求如确需保留审计，使用受控元数据或显式有界保留策略，不应无上限保留完整原文；清理必须保护所有已受理输入、事实、验收和执行证据引用。

### 验收标准

- [ ] 队列已满时提交一组不同内容请求，均被拒绝且不新增正式业务对象引用；若采用暂存方案，其容量受限并能在有界清理后回归基线。
- [ ] Typed 业务回调主动返回错误，业务、请求状态与对象引用不出现不受控残留；暂存采用同样回收标准。
- [ ] 并发请求竞争最后一个队列名额，只有允许数量被受理，失败方不能绕过归档配额。
- [ ] 清理/重启恢复不删除已有有效引用；合法同请求重试仍只产生一次业务效果。

## AUD-04 / P2：来源文件大小检查晚于全量读取

**代码位置：** [`src/core/work.go`](https://github.com/ExplodeCode6324/Secretary_Simplified/blob/ac281ac2e3504ef215f9b69ee1b314e2db16adea/src/core/work.go)，`source.sync` 分支。

### 问题描述与触发条件

先 `os.ReadFile(path)`，后检查 `len(b) > 1<<20`。配置误指向大文件时，需要先完整读入内存才能返回 `INPUT_TOO_LARGE`。1 MiB 限制目前只约束后续解析，不能约束读取阶段资源使用。

### 修改建议

打开文件后最多读取“上限 + 1 字节”，超限立即拒绝，正确关闭句柄。读前文件大小检查可作快速拒绝，但不能是唯一保护，因为文件可能在检查后增长。必要时拒绝非普通文件，避免来源读取无限阻塞。

### 验收标准

- [ ] 超过 1 MiB 的文件返回 `INPUT_TOO_LARGE`，读取缓冲不随整个文件大小线性增长。
- [ ] 边界大小、超出一字节、读前检查后继续增长的文件，都受到实际读取上限保护。
- [ ] 正常小文件导入不回归；拒绝/读取失败不错误推进成功游标，不删除旧来源记录，不产生成功回执。

## GATE-01：真实来源不能复用固定 SYNTHETIC 的 fixture 导入

**代码位置：** [`src/ingest/fixture.go`](https://github.com/ExplodeCode6324/Secretary_Simplified/blob/ac281ac2e3504ef215f9b69ee1b314e2db16adea/src/ingest/fixture.go)、[`src/core/work.go`](https://github.com/ExplodeCode6324/Secretary_Simplified/blob/ac281ac2e3504ef215f9b69ee1b314e2db16adea/src/core/work.go)。

### 问题描述

当前 `source.sync` 调用合成适配器，来源状态、原文对象与来源记录固定标为 `SYNTHETIC`（合成资料）。这是 M1—M3 合成阶段边界，**不是宣称已有合成验证无效，也没有证据表明已经泄露真实资料**。

但不能把 `fixture_path` 替换成真实文件就开始 M4。误分类会影响后续披露、诊断归档和公开证据判断。普通 CLI/API 默认 `PERSONAL`（个人资料）是另一条入口；不能通过 `--data-class SYNTHETIC` 绕过真实输入的外发拒绝。

### 修改建议

本轮二选一，明确记录所选接入范围：

1. **仅受控文字试运行：**真实输入使用现有 PERSONAL 入口；明确授权对应提供方和数据范围，禁止真实文件进入 fixture，暂不开放真实来源文件同步。
2. **需要真实来源同步：**增加来自受控来源注册/配置的可信分类及来源权限，沿 SourceState、ObjectRef、SourceRecord 和派生产物传播；缺失或非法分类拒绝，不能由不可信文件正文自行声明低分类。

禁止静默扩宽 ProviderPolicy（模型披露策略），SECRET（秘密资料）仍不得外发。

### 验收标准

- [ ] 文档和配置明确区分合成 fixture 与真实入口；不能用改路径/改低分类的方式绕过真实接入。
- [ ] 选择仅文字试运行时，证明普通输入默认 PERSONAL、未授权时模型不接收、授权正向用例正常；真实来源同步明确列为未开放。
- [ ] 选择开放真实来源时，使用虚构的 PERSONAL/SENSITIVE 测试内容验证整条分类传播、来源权限和低分类伪造拒绝。
- [ ] 未授权类别/来源不外发，SECRET 测试标记不进入模型或诊断转储；不能把误标真实内容作为合成证据发布。

## GATE-02：全量披露检查造成同库不同权限资料相互阻断

**代码位置：** [`src/context/context.go`](https://github.com/ExplodeCode6324/Secretary_Simplified/blob/ac281ac2e3504ef215f9b69ee1b314e2db16adea/src/context/context.go)，`Build()` / `CheckDisclosure()` / `selectRelevant()`；[`src/store/memory_repo.go`](https://github.com/ExplodeCode6324/Secretary_Simplified/blob/ac281ac2e3504ef215f9b69ee1b314e2db16adea/src/store/memory_repo.go)，`Snapshot()`。

### 问题描述

先加载全量快照并检查披露，再选择当前相关内容。无关的禁止外发事项、未授权来源或缺失可信分类的旧派生记录，也可能阻断普通请求。来源快照当前包含全部来源状态，禁用来源不等于自动退出披露检查。

这是**保守拒绝带来的可用性限制**，不是权限绕过。不得以移除分类检查、自动降级分类或给全部数据扩权来修复。

### 修改建议

**本轮允许最小隔离方案收口，不强制重构：**使用独立数据目录保存明确允许用于本轮模型交互的资料，禁止与仅本地/未知分类数据混用；在操作说明中写明现有同库限制和受支持范围。

如要支持同库混合权限，应另行实现允许使用的相关投影，再对实际依赖合并分类，并在模型调用前复核；保留“省略不等于不存在”的语义。不应把这一架构扩展自动升级成本轮全部必做内容。

### 验收标准

- [ ] 记录选择“独立数据目录隔离”还是“同库投影隔离”，以及当前承诺的支持范围。
- [ ] 采用最小方案时：两个独立目录分别放允许外发与仅本地测试资料，前者正常工作，后者不会进入前者上下文；明确说明同库混放仍可能拒绝。
- [ ] 采用同库方案时：无关禁止外发记录不影响允许范围请求；显式触及禁止内容时仍拒绝或明确省略，未知派生分类不自动降级。
- [ ] 不把来源禁用等同于披露授权；新增或恢复来源后权限边界仍然有效。
